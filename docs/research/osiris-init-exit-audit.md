# Osiris INIT / EXIT audit — StoryEditor

Дата: 2026-11-13. Проверен оригинальный `C:\Divine Divinity\main\startup\story.000` v1.4.

## Результат по бинарному файлу

- Goals: **478**.
- INIT actions: **5 433**.
- EXIT actions: **449**.
- Отдельный file-level `GlobalActions`: **0**.
- Параметры-переменные (`Kind=1`) в INIT/EXIT: **0**.
- Действия с флагом `NOT`: **13 INIT**, **52 EXIT**.
- Анонимные control records: **1 INIT**, **0 EXIT**. Единственная запись соответствует `!1;`.

## Что уже умеет StoryEditor

1. `StoryReteExporter` читает INIT и EXIT из каждой записи Goal в `StoryGoalRecord`.
2. `StoryDivDecompiler.RenderGoals` выводит обе секции каждого Goal через `RenderActionList`.
3. `RenderActionList` обрабатывает обычные вызовы, литералы, префикс `NOT` и анонимные control records (`GoalCompleted;`, `!n;`).
4. `StructureParser` распознаёт `INIT` и `EXIT` как отдельные структурные секции.
5. WPF-редактор показывает их в отдельных `InitEditor` и `ExitEditor`; оба контрола теперь доступны для редактирования.
6. Изменения INIT/EXIT сохраняются в общем наборе `EditedSection` по исходным диапазонам, поэтому можно менять секции нескольких Goals и переключаться между ними до сохранения.
7. `ProcedureAnalysisFeature` индексирует вызовы процедур в KB, INIT и EXIT и позволяет перейти к месту вызова.

INIT/EXIT теперь можно редактировать в UI; Save по-прежнему создаёт отдельную копию `.div`, а Build перед запуском оригинальной OsirisDLL проверяет структуру секций и известные сигнатуры API.

Декомпилированный файл `%TEMP%\StoryEditor_InitExit_Audit\startup.div` сравнен с исследовательской реконструкцией `03_osiris\story_000_full_source_candidate.div.txt` из архива декомпиляции.

| Секция | StoryEditor | Reference candidate | Различия после нормализации |
|---|---:|---:|---:|
| INIT | 5 433 | 5 433 | **0** |
| EXIT | 449 | 449 | **0** |

Нормализация учитывала два различия представления, не меняющие значение: shortest-roundtrip float32 (`0.9`) против более длинной десятичной записи (`0.899999976`), а также пробел после `!` (`!1;` / `! 1;`). Float-литералы сравнивались по IEEE-754 binary32 bits. Порядок действий и их значения после такой нормализации совпали.

Это подтверждает согласованность вывода StoryEditor с восстановленным reference candidate. Это **не** доказывает восстановление исторического авторского `story.div` побайтно.

## Ограничения текущего редактора

- INIT/EXIT редактируются как полные текстовые секции. Отдельного AST с операциями над отдельными action nodes и автоматическим форматированием пока нет.
- `ActionListParser` проверяет структуру секции, завершение действий `;`, скобки, `NOT`, `GoalCompleted;`, `!n;`, а также синтаксис вызовов.
- `ApiSymbolCatalog` теперь извлекает типы и направления параметров из объявлений API. Для известных `call`/`syscall` проверяются арность и очевидные несовпадения типов литералов/объявленных объектов. Имена без API-декларации разрешены: это могут быть пользовательские Osiris facts. Полная проверка выражений, переменных и семантики движка не заявляется.
- `ProcedureAnalysisFeature` извлекает вызовы лексически для перекрёстных ссылок. Это не семантическая проверка аргументов.
- Основная `RuleParser` ориентирована на KB-правила IF/PROC, а не на полноценное редактирование lifecycle actions.
- При сборке исходный OsirisDLL остаётся окончательным компилятором/проверкой синтаксиса.
- Если `GlobalActions` не пуст, `StoryDivDecompiler` пока не выводит этот отдельный раздел и добавляет диагностическое предупреждение. В проверенном startup story список пуст, поэтому этот пробел не затрагивает текущие 478 Goals.

## Проверка компиляции и roundtrip INIT/EXIT

В ходе проверки полного исходника оригинальный OsirisDLL обнаружил 18 ошибок типов параметров в заголовках Story-процедур (PROC с анонимными слотами). Причина была не в изменениях INIT/EXIT: бинарная запись хранит типы параметров PROC, но декомпилятор выводил неизвестные слоты как голый wildcard.

Исправление в StoryDivDecompiler:

- Для FunctionKind=5 тип каждого параметра берётся из StoryFunctionRecord.TypeValues.
- Неизвестный слот выводится как типизированная, но неиспользуемая переменная, например (INTEGER)_VarN. Поскольку такая переменная не используется в условиях/действиях правила, она сохраняет поведение wildcard и не связывает его с переменными тела PROC.
- Для PROC-заголовков фактическая арность берётся из типизированной сигнатуры, а не из ширины массива адаптера. Это также защищает заголовки от хвостовых нулей, добавляемых Osiris Load/Save при выравнивании адаптеров.
- Регрессионный тест проверяет типы, отсутствие повторного использования ID переменных тела и обрезку padding до фактической арности.

После исправления выполнен полный эксперимент на временной копии startup Story:

1. Декомпиляция: 478 Goals, 4 918 KB rules, 5 433 INIT actions, 449 EXIT actions.
2. Исходник успешно скомпилирован оригинальным 32-разрядным OsirisDLL и объединён с временной копией base Story.
3. Результат прошёл LoadStoryCheck.ps1: OSIRIS LOAD SUCCEEDED, 1 175 functions, 10 759 Rete nodes.
4. В тестовом INIT изменено SetTime(ENGINE_GAME, 10) на SetTime(ENGINE_GAME, 11); в EXIT — SetQuestCompleted(36) на SetQuestCompleted(37).
5. Повторная декомпиляция собранного бинарника подтвердила наличие обоих изменённых значений.

Результат: INIT → OsirisDLL compile → binary → decompile → INIT подтверждён; EXIT → OsirisDLL compile → binary → decompile → EXIT подтверждён. Все входы/выходы эксперимента находились во временном каталоге; установленные игровые файлы и сохранения не изменялись. Саму игру с этим бинарником пока не запускали.

## Цветовая подсветка

OsirisColorizer используется во всех трёх AvalonEdit-контролах — KB, INIT и EXIT. Единая палитра различает ключевые слова, строки, числа, переменные, объекты, типы, API-функции по категориям, вызовы Story-процедур, комментарии, директивы, операторы и разделители. Подсветка KB обновляется после короткой паузы ввода, INIT/EXIT — непосредственно при редактировании. Подсказки редакторов объясняют основные цвета.
